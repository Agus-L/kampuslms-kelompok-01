Buat form tambah mata kuliah, isi dengan data yang pasti tidak valid (SKS = 99), kirim, lalu jawab:
1. Method apa yang menerima request? Di 
controller mana?
Jawaban: Diterima oleh method store() di dalam file CourseController.php. Saat tombol "Simpan" diklik, form mengirim data lewat HTTP POST ke URL /courses. Route Laravel langsung mengarahkan request tersebut ke controller CourseController.php, tepatnya pada method public function store(StoreCourseRequest $request).

2. Di titik mana persisnya validasi terjadi — sebelum atau sesudah baris pertama method controller?
Jawaban: Validasi terjadi sebelum baris pertama method controller dieksekusi. Karena di controller kita menggunakan Form Request khusus (StoreCourseRequest), Laravel langsung memeriksa aturan validasi (seperti batas SKS min 1 dan max 6) sebelum masuk ke dalam isi method store(). Jadi ketika SKS diisi 99 (tidak valid), Laravel langsung menyetop proses dan membalikkan user sebelum baris pertama ($validated = $request->validated()) sempat dijalankan sama sekali.

3. Ke mana Laravel me-redirect setelah gagal? Siapa yang menentukan tujuannya?
Jawaban: Laravel me-redirect pengguna kembali ke halaman formulir sebelumnya. Yang menentukan tujuannya adalah sistem internal Laravel secara otomatis di balik layar.
Penjelasan Alur & Apa yang Terjadi di File: Ketika validasi di baris pertama tadi gagal, controller tidak melanjutkan proses ke view atau ke database. Laravel secara otomatis menangkap kegagalan tersebut dan memeriksa informasi riwayat browser dari header HTTP (Referer) untuk mencari tahu dari halaman mana formulir itu dikirimkan. Setelah mengetahui asalnya, Laravel secara mandiri membuat respons pengalihan (HTTP status 302 Redirect) yang memerintahkan browser untuk memuat ulang halaman form tambah data tanpa perlu kita tulis perintah redirect-nya secara manual.

4. Dari mana @error('sks') mengambil pesannya?
Jawaban: Mengambil dari memori sementara server (Session flash data), tepatnya lewat penampung bawaan Laravel yaitu variabel $errors.

Penjelasan Alur & Apa yang Terjadi di File: Saat proses validasi di controller tadi gagal, Laravel secara otomatis membuat kalimat komplain (misalnya: "The sks field must be between 1 and 8"). Pesan ini kemudian dititipkan sementara ke dalam Session server sebelum perintah redirect dikirim. Ketika browser membuka kembali file tampilan create.blade.php
, arahan @error('sks') bertugas mengecek isi session tersebut. Jika ditemukan ada catatan kesalahan khusus untuk kolom sks, Blade langsung mengambil teks pesan tersebut melalui variabel $message dan menampilkannya sebagai teks peringatan merah di layar.

5. Dari mana old('sks') mengambil nilainya? Berapa lama nilai itu bertahan?
Jawaban: Mengambil nilainya dari Session flash data (rekaman input lama), dan nilainya hanya bertahan selama satu kali request saja. Supaya user tidak kesal mengetik ulang dari awal saat gagal validasi, Laravel otomatis menyelamatkan angka 99 tadi ke dalam session. Fungsi old('sks') di form bertugas mengambil kembali angka tersebut dan memasukkannya ke kolom input. Karena sifatnya hanya flash data (sementara), begitu halaman selesai dimuat data itu langsung dihapus. Kalau halaman di-refresh (tekan F5), isinya akan langsung hilang dan form kembali kosong.

Jika pada model proteksi `$fillable` tidak didefinisikan dengan ketat, kolom sensitif database bisa dijebol dan disusupi nilai liar dari penyerang. |

| 4 | Hapus validasi `in:...` pada `status`, kirim `status=superadmin` | Server akan menolak karena nilai status tidak sesuai dengan opsi resmi form (`draft`, `active`, `archived`). | Validasi Laravel berhasil dijebol dan tidak memunculkan pesan error form biasa. Nilai `status=superadmin` lolos sampai ke database, lalu memicu crash **HTTP 500 `QueryException`** dengan pesan `SQLSTATE[23000]: Integrity constraint violation: 19 CHECK constraint failed: status`. Hal ini membuktikan bahwa tanpa `Rule::in()`, filter whitelist di level aplikasi hilang, sehingga database SQLite yang harus menolak secara kasar lewat CHECK constraint (merusak user experience). |
| 5 | Hapus `->withQueryString()`, lakukan pencarian lalu klik halaman 2 | Hasil pencarian dan filter akan tetap bertahan saat pengguna berpindah ke halaman berikutnya. | **Filter pencarian hilang total saat berpindah halaman.** URL berubah dari `/courses?q=a` menjadi hanya `/courses?page=2` (parameter `?q=a` terhapus dari URL). Akibatnya, halaman 2 menampilkan kelanjutan dari seluruh data mata kuliah umum, bukan halaman 2 dari data yang sedang dicari, serta kotak pencarian ter-reset menjadi kosong. Hal ini membuktikan bahwa tanpa `->withQueryString()`, tautan pagination Laravel hanya menyertakan nomor halaman dan membuang semua query string URL yang sedang aktif. |
| 6 | Ganti `return redirect()` menjadi `return view()` pada `store()`, lalu tekan F5 setelah simpan | Halaman daftar mata kuliah akan tampil biasa dan me-refresh halaman tidak akan mempengaruhi atau menduplikasi isi database. | **Terjadi pengiriman ulang form (*duplicate form submission*) yang memicu data ganda.** Penggunaan `return view()` melanggar pola **PRG (Post/Redirect/Get)** karena server langsung merespons request POST dengan tampilan HTML tanpa pengalihan URL. Akibatnya, browser mencatat bahwa request terakhirnya adalah `POST /courses` beserta seluruh payload formnya. Saat pengguna menekan F5 (Refresh), browser mendeteksi pengulangan aksi mutasi data sehingga memunculkan dialog peringatan *"Confirm Form Resubmission"*. Jika dikonfirmasi, browser mengeksekusi ulang request POST yang sama ke server, menyebabkan data tersimpan ganda atau memicu error `Unique constraint failed: courses.code`. Hal ini membuktikan fungsi krusial `return redirect()` untuk mereset riwayat request terakhir browser menjadi `GET` (HTTP 302), sehingga aksi refresh pengguna hanya memuat ulang tampilan biasa tanpa menyentuh database. |
